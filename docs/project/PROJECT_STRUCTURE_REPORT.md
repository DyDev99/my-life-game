## 0. Headline findings

| # | Finding | Severity |
|---|---------|----------|
| 1 | **The repo has zero commits.** Every file is untracked, so a bad move cannot be undone. The 41 MB of binaries (`.blend`, `.zip`, preview PNGs) also need a decision *before* the first commit, because once they're in git history they can't easily be removed. | **Blocker** |

The Unity-style target layout (`Assets/_Project/…`, Prefabs, Scenes) does not apply here and has been adapted for the web stack. | High (docs/architecture drift) |

| 6 | **God store.** `src/store/gameStore.ts` (1,186 lines) mixes UI routing, player, time, vehicles, inventory, journal, sports minigames, and every activity action. 28 files import it. | Medium |
| 7 | **God components.** `VehiclesAndCharacters.tsx` (1,832 lines), `Buildings.tsx` (1,484), `SportsCity.tsx` (1,274): 1,026 `<mesh>` elements and ~560 hard-coded positions in total, with no instancing. | Medium |
| 8 | **About 41 MB of duplicated or unused files** at the root and in `public/` (details in §4). | Medium |
| 9 | **No tests, no CI, ESLint fails (24 errors).** TypeScript and `next build` both pass. | Medium |

## 3. Source code analysis

### 3.1 Dependency graph (simplified)

```text
app/page.tsx ──► screens/*, ui/* (15 modals + HUD), game/GameCanvas (dynamic, ssr:false)
game/GameCanvas ──► CameraController, KeyboardController, GameWorld
game/GameWorld ──► Buildings, Environment, VehiclesAndCharacters, NPCSystem, SportsCity,
                   CityTrafficSystem, DayNightLighting
game/CityTrafficSystem ──► VehiclesAndCharacters   (reuses Supercar/Motorbike/Remork)
ui/CharacterSwitcherModal ──► game/3DAssetLoader    (UI → 3D layer, renders its own preview canvas)
store/gameStore ──► lib/sound/audioManager           (state layer triggers side effects)
28 files ──► store/gameStore
```

No circular imports were found. There are two layering smells:
- **The store calls audio directly** (`gameStore.ts` imports `audio`). The state layer has side effects, which makes actions hard to unit-test.
- **UI imports from the 3D layer** (`CharacterSwitcherModal` → `3DAssetLoader`). This is acceptable, but the loader belongs in a shared `assets` module.

### 3.2 File size hotspots

| File | Lines | Problem |
|------|------:|---------|
| `components/game/VehiclesAndCharacters.tsx` | 1,832 | 5 unrelated exports: Motorbike, Bicycle, RemorkTukTuk, Supercar, PlayerCharacter (with procedural fallbacks) |
| `components/game/Buildings.tsx` | 1,484 | 16 building components plus interaction plus collider registration |
| `components/game/SportsCity.tsx` | 1,274 | 12 exports: a whole district (stadium, courts, plaza, NPCs, minigames) |
| `store/gameStore.ts` | 1,186 | God store (see §3.3) |
| `components/ui/CharacterSwitcherModal.tsx` | 744 | Modal with its own 3D preview canvas and a duplicate roster |
| `components/ui/HUD.tsx` | 642 | Subscribes to per-frame values (see §6) |
| `components/game/Environment.tsx` | 609 | Trees, paddies, river, lamps, and the ground click-to-move handler |

### 3.3 `gameStore.ts` responsibilities (should be separated)

1. **Session/UI routing:** `screen`, `activeModal`, `phoneApp`, `language`, `soundEnabled`
2. **Player profile & stats:** `player`, `stats`, `relationships`, `inventory`, `journal`, `statPops`
3. **Time & day cycle:** `day`, `timeHour`, `advanceTime`, `sleepAndEndDay`, `startNextDay`, `dayHistory`, `lastDaySummary`
4. **Movement / transient per-frame state:** `playerPos`, `targetPos`, `playerHeading`, `movementState`, `currentSpeed`, `cameraMode`, `cameraFocus`
5. **Vehicles:** `ridingVehicle`, `vehicleSpeed`, `nearVehicle`, `supercarPos/Heading`, mount/dismount (uses `setTimeout`)
6. **World data:** `LOCATION_COORDINATES` (static data living in the store module)
7. **Activities (game rules):** `performWork`, `performRest`, `performCafeDrink`, `performPagodaMerit`, `performMarketBuy`, `performHotelStay`, … About 9 near-identical blocks each build a journal entry with `formatTimeHour(state.timeHour)`, which is duplicated logic.
8. **Sports minigames:** `goalsScored`, `volleyballRallies`, `selectedJersey`, `scoreFootballGoal`, …

### 3.4 Duplicated data and logic

| What | Where it is defined |
|------|---------------------|
| Character roster (id → model/portrait/name/career) | `CharacterCreation.tsx`, `CharacterSwitcherModal.tsx`, `VehiclesAndCharacters.tsx`, `gameStore.ts` (`switchCharacter` union type): **4 places** |
| Character FBX path map | `CharacterSwitcherModal.tsx:28-33` and `VehiclesAndCharacters.tsx:846-851` (copy-paste) |
| Asset URLs | 43 string literals spread across 7 files; there is no asset registry |
| Avatar id union `"sokha" \| "sreyneath" \| …` | Repeated inline instead of one exported `CharacterId` type |
| Modal id and phone app unions | Repeated inline in the state type and the action signatures |
| Journal-entry construction | ~9 copies in `gameStore.ts` |
| World coordinates | `LOCATION_COORDINATES` (store), collider boxes (`collisionSystem.ts` + `Buildings.tsx`), and ~560 literal positions in components. Moving a building means editing 2–3 places. |

### 3.5 Global state and singletons

- `collisionWorld` (module singleton, `lib/game/collisionSystem.ts`): colliders are registered from components. On HMR or remount they can double-register unless that path is cleared (needs verification).
- `audio` (module singleton, `lib/sound/audioManager.ts`). This is a reasonable pattern for Web Audio.
- `modelCache` / `loadingPromises` (module maps in `3DAssetLoader.tsx`). These are fine, but nothing ever disposes of them.

These are not excessive for a project of this size. The problem is the **store-to-audio coupling**, not the singletons themselves.

## 4. Duplicates and unused files

All of these were verified by byte comparison (`cmp`/`md5`) and by grepping `src/` for every asset path. Nothing has been removed.

### 4.1 Exact duplicates

| File | Duplicate of | Size |
|------|--------------|------|
| `./kampong_cham_scene.png` | `public/kampong_cham_scene.png` (identical) | 2.0 MB |
| `./mylife_kit.py` | `MyLife_Blender_Kit.zip → MyLife_Blender_Kit/mylife_kit.py` (identical, v0.1) | 120 KB |
| `MyLife_Blender_Kit.zip` (174 export files) | All 174 match `public/models` + `public/sprites` byte-for-byte | 12 MB |
| `public/sprites/chandy_closeup.png`, `chandy_turnaround.png` | `…_new_charector/Previews/` (identical) | 3.7 MB |
| `public/models/Vehicles/Supercar/**` | `…/Supercar_Asset/` LOD FBX + Textures (identical) | 2.6 MB |
| `public/models/Characters/CHR_Chandy.fbx` + 7 Chandy portraits + `char_chandy_full.png` | `…_new_charector/` (identical) | — |

So the zip is a full copy of what the game ships today, plus the v0.1 `.blend` and script. It is the **only remaining copy of the v0.1 `.blend`**. If the v0.1 source matters, archive the zip rather than delete it.

### 4.2 Near-duplicates (version drift, v0.1 in `public/` vs v0.2 in the kit)

| Group | Diff | Interpretation |
|-------|------|----------------|
| Buildings / Props / Nature / Vehicles FBX (43 files) | 50–150 bytes each | Most likely only export timestamps/metadata, so content is the same |
| Character FBX: Sokha, Sokunthea, Sreyneath, Taing, Vuth | ~125,000 bytes (`CHR_Sokha`) | **Real geometry/rig change** in v0.2. The game uses the old v0.1 characters. |
| 126 sprites | consistently ~6 KB larger in v0.2, same dimensions | Re-rendered. Needs a visual check to tell whether they intentionally changed. |

**Decision needed:** should `public/` be re-synced to kit v0.2? This is an art decision, not a cleanup decision. The v0.2 characters must be checked in-game (scale, rig, blendshapes) before switching.

### 4.3 Unused (no reference found in `src/`, configs, or CSS)

| Path | Size | Notes |
|------|-----:|-------|
| `public/file.svg`, `globe.svg`, `next.svg`, `vercel.svg`, `window.svg` | 3 KB | create-next-app template leftovers |
| `public/kampong_cham_scene.png` | 2.0 MB | preview render |
| `public/sprites/chandy_closeup.png`, `chandy_turnaround.png` | 3.7 MB | preview renders |
| 31 of 58 FBX in `public/models` | 4.7 MB | All 14 props, 4 of 5 shophouse/stall variants, `StiltHouse` (A), 8 nature tiles/variants, `VEH_Bicycle`, Supercar LOD0/2/3 |
| `public/sprites/{Icons,Thumbnails,UI,Characters}` | ~5.6 MB | The HUD uses lucide icons instead; only 6 portraits and 5 inventory icons are referenced |

**Not safe to delete.** These are the game's planned asset library (the GDD MVP scope uses props, tiles, and the bicycle), and `public/` files can be requested by URL at runtime. The correct action is to **keep them and document which are "wired" vs "available"**. They cost deploy size only, not runtime download, because nothing requests them.

Note: `Bicycle` exists in code as a procedural mesh and in the store (`ridingVehicle: "bicycle"`), but it does not load `VEH_Bicycle.fbx`. It is a likely candidate to wire up later.

### 4.4 Implicit (non-obvious) references to protect during any move

| Reference | Risk |
|-----------|------|
| `CAR_Supercar_LOD*.fbx` → `Textures/T_*.png` | The FBX embeds texture paths (`/tmp/car_out/Textures/T_Carbon.png`, …). `FBXLoader` resolves them **relative to the FBX's folder**, so `Textures/` must stay next to the FBX files. |
| All `/models/...` and `/sprites/...` URLs | Plain strings in components and in the store's initial inventory. Renaming `public/` folders breaks them silently at runtime: no compile error, only a 404 and the procedural fallback. |
| Character ids (`"sokha"` etc.) | Used as keys across store, UI, and 3D. They must stay stable. |
| `@/*` path alias | `tsconfig.json` maps `@/*` → `./src/*`. Moving folders inside `src/` is safe as long as imports are updated. |

## 6. Performance risks (report only, no changes made)

| # | Issue | Evidence | Impact |
|---|-------|----------|--------|
| P1 | Per-frame store writes cause React re-renders | `KeyboardController.tsx:439` `setMovementState(state, currentSpeed.current)` every frame. Subscribers: `HUD.tsx:52-53`, `VehiclesAndCharacters.tsx:881-882`, `CameraController.tsx:13`. Same pattern for `vehicleSpeed` (subscribed in 5 places). | **High.** A 642-line HUD tree re-renders ~60×/s while moving. |
| P2 | 17 street lamps each mount a `pointLight` at night | `Environment.tsx:372` `{isNight && <pointLight/>}` × 17 lamps (+3 other pointLights and 5 spotLights elsewhere) | **High on mobile.** Changing the light count forces three.js to recompile every material, causing a hitch at dusk and dawn. Forward rendering with ~20 point lights is expensive. |
| P3 | No instancing | 1,026 `<mesh>` JSX elements, 0 `instancedMesh`/`<Instances>`. Trees, lamps, stools, paddies, and stadium seats are individual draw calls. | Medium–High: draw-call bound on mobile |
| P4 | FBX loaded at runtime | `FBXLoader` parses on the main thread. `CHR_Chandy.fbx` 435 KB, `CAR_Supercar_LOD1.fbx` 743 KB. | Medium. GLB + Draco/meshopt is typically 3–10× smaller and faster to parse. |
| P5 | Texture maps discarded | `enhanceMaterial()` builds a new `MeshStandardMaterial` copying only `color`, which drops `map`/`normalMap`. The Supercar textures are still fetched (≈350 KB) and then thrown away, and the original materials are never disposed. | Medium (wasted bandwidth/GPU memory, plus lost visual detail) |
| P6 | LODs exported but not used | Only `CAR_Supercar_LOD1` is loaded; there is no `<Detailed>`/LOD switching | Low–Medium |
| P7 | Shadow cost | `PCFShadowMap`, 2048² directional map, `castShadow` on most meshes | Medium on mobile (GDD target: 3 GB Android, 30 fps) |
| P8 | Impure render | `Math.random()` during render (lint errors). Layouts reshuffle on every re-render, and with P1 that can happen every frame. | Low–Medium (correctness + perf) |
| P9 | Unused files in `public/` | ~11 MB of unreferenced sprites/previews/FBX | Deploy size only |
| P10 | Large source binaries in repo root | `.blend` 12 + 6 MB, zip 12 MB, previews ~15 MB | Repo size/clone time (needs Git LFS) |

`Documentation/PerformanceAudit.md` will expand these findings in the documentation phase.

## 7. Architecture problems summary

| Smell | Where | Recommendation (keep it simple) |
|-------|-------|---------------------------------|
| God store | `gameStore.ts` | Split into Zustand **slices** in one store (same `useGameStore` API, so no consumer changes). Move static data out. |
| God components | `VehiclesAndCharacters`, `Buildings`, `SportsCity` | One file per vehicle/building/district piece; keep the group under a feature folder |
| Duplicate roster/data | 4 files | One `data/characters.ts` and one `data/locations.ts` as the single source of truth |
| Hard-coded asset URLs | 7 files | One `assets/assetPaths.ts` registry |
| State layer has side effects | store → audio | Move sound triggers to subscribers/UI, or isolate them in one `effects` module |
| Transient data in React state | `currentSpeed`, `vehicleSpeed`, positions | Keep in refs or a non-reactive store; push to React only on threshold changes |
| Domain logic mixed into JSX | Activities, minigame scoring | Move pure rules to `game/rules/*` (testable without React) |
| No save system | No `persist` | Planned feature: Zustand `persist` on a *serialisable* slice only |
| Docs say Unity | GDD §2, kit READMEs | ADR-0001: "Web runtime (Next.js + R3F) chosen; Unity kit scripts unused" |

Over-engineering to **avoid**: no ECS, DI containers, event buses, or service locators. The project is ~13k lines with one developer. Folders by feature, slices in one store, and pure functions for rules are enough.

## 8. Dependency risks for migration

1. **No version control.** Commit a baseline first (see the plan, step 0).
2. **Runtime string URLs** to `public/` are not type-checked. Introduce the asset registry **before** any rename in `public/`, and smoke-test in the browser (watch the Network tab for 404s; the procedural fallbacks hide failures visually).
3. **Supercar texture folder** must move together with its FBX files.
4. **`'use client'` boundaries:** moving files does not change them, but `GameCanvas` must stay behind `next/dynamic({ ssr:false })`.
5. **Next.js 16 conventions:** `src/app/` is the router root, and only route files belong there. Don't put game code under `app/`.
6. **Collider registration side effects** in `Buildings.tsx`: if components are split, each one must keep its `collisionWorld` registration.
